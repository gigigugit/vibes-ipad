## Plan: Synthetic Response Pipeline

Build a template-first synthetic-data workflow around the repo's existing per-domain template assets, keep generation/review records structured while editing, and export an output-only JSONL at the end for model training. Use `template_config/*.json` plus `templates/templates_*.txt` as the source of truth for generation, avoid coupling new work to the legacy root `templates.txt`, and implement a lightweight localhost review app so batches can be corrected quickly before export.

**Steps**
1. Phase 1: Normalize generation inputs.
2. Choose the generation source of truth and document it explicitly: use the per-domain registry in `template_config/*.json` and the matching template bodies in `templates/templates_*.txt`; treat the root `templates.txt` as legacy/reference content only. This step blocks the rest because the generator needs one canonical template source.
3. Define an intermediate authoring schema for generated rows with fields such as `id`, `domain`, `template_name`, `scenario`, `tags`, `slot_values`, `draft_text`, `edited_text`, `status`, and `notes`. Final export remains output-only JSONL, but the review workflow should not discard metadata before approval. This step blocks both generator and review UI.
4. Expand domain catalogs in parallel with scenario catalogs. One track should normalize the provided medication catalog in `medication lists.md` into slot-compatible domain records, using canonical labels plus aliases/tags for Birth Control, Hair Loss, Performance Anxiety, and Sexual Health, while explicitly flagging that Photoaging and Testosterone Deficiency medication catalogs are still missing from the provided source. The other track should enumerate scenarios per domain such as initial treatment, follow-up, change medication, cadence change, dose-number change, side effects, worsening symptoms, inadequate response, revert to prior medication, and refill/logistics. These two tracks can run in parallel once the schema is defined.
5. Phase 2: Build deterministic generation.
6. Implement a synthetic-data generator that reads the domain template registry, fills placeholders from medication/scenario catalogs, and emits structured authoring rows. Keep generation deterministic and reproducible first by using explicit combinations or seeded sampling rather than free-form LLM generation. This depends on steps 2-4.
7. Add a controlled variation layer on top of the deterministic generator to diversify voice, sentence ordering, and phrasing without changing the format. Start with rule-based variant banks per scenario; make LLM-based paraphrasing optional and gated behind a separate command so the default dataset remains auditable. This depends on step 6.
8. Add validation rules that catch malformed rows before review: missing placeholders, unfilled braces, domain/template mismatch, invalid medication insertion, duplicate near-identical rows, and section-structure violations. This can be built in parallel with step 7 once the base generator exists.
9. Phase 3: Build the review workflow.
10. Create a lightweight localhost review app using a minimal Python web stack with no frontend build step, preferably Flask plus server-rendered templates. The review UI should load generated batches, show one row at a time or in small pages, support in-browser editing, and expose approve/reject/skip actions. This depends on step 3 and can start after a minimal generator exists from step 6.
11. Structure the review UI around practical reviewer tasks instead of generic browsing: filter by domain, scenario, medication, and approval status; compare generated text with its template/scenario metadata; flag duplicates; and allow quick keyboard-driven edits. Persist review state to a structured batch file so edits are resumable.
12. Add export actions that generate two outputs from approved rows: a primary output-only JSONL for training, and a secondary audit/export file preserving metadata for regeneration, QA, and future deduplication. This depends on steps 10-11.
13. Phase 4: Seed and iterate.
14. Start with a small pilot corpus per active domain using the currently represented domains: Hair Loss, Sexual Health, Performance Anxiety, Birth Control/Contraception, Photoaging, and Testosterone Deficiency if it remains in template assets. Generate small deterministic batches first, review them, then widen scenario and medication coverage only after the review loop feels fast enough.
15. After the pilot, add near-duplicate controls and coverage reporting so each batch can answer: which domains, templates, scenarios, and medications are represented; which combinations are missing; and which rows were edited heavily and should become new templates or variant banks. This depends on steps 8 and 12.

**Medication Normalization Spec**
1. Parse the source file into domain-scoped records first, using markdown headings as the only trusted boundary markers. Treat top-level headings such as Birth Control, Hair Loss, Performance Anxiety, and Sexual Health as `domain` values; treat lower-level headings such as Male pattern hair loss, Female pattern hair loss, FDA-approved, Personalized compounded oral PDE5i tablets, and SSRIs for premature ejaculation as `subdomain` or `category` tags rather than new domains.
2. Normalize each medication into one canonical record per clinically distinct option. Do not create a separate canonical record for each alias or brand synonym. Canonical records should be generated from the physician-facing or EMR-facing label when one is present; aliases should attach to that record.
3. Use this target schema for normalized medication records: `id`, `domain`, `subdomain`, `canonical_label`, `display_label`, `aliases`, `brand_equivalents`, `active_ingredients`, `strength_text`, `strength_values`, `form`, `route`, `cadence`, `pill_count_options`, `tags`, `source_text`, `notes`, `status`. This schema is for the implementation pipeline and can later be flattened for generation.
4. Required field rules: `id`, `domain`, `canonical_label`, and `source_text` are always required. `subdomain` is required when the source section clearly partitions clinically different groups, such as male vs female pattern hair loss or PDE5i vs SSRI-for-PE. `display_label` defaults to `canonical_label` when no separate EMR display name is needed. `status` should default to `active`.
5. ID generation rule: create deterministic IDs from normalized domain plus canonical label, for example slug-style values such as `birth-control__levonorgestrel-0-1mg-ee-0-02mg` or `sexual-health__climax-control-tadalafil-fluoxetine-daily`. IDs must be stable across reruns so review edits and generated-row references do not break.
6. Canonical-label rule: prefer the exact physician-facing medication string that should appear in synthetic output, stripped of parenthetical commentary that is metadata rather than core name. Keep dosage and clinically meaningful formulation details in the canonical label when they distinguish real options. Example: keep “Chewable Tadalafil PRN” and “Chewable Tadalafil Daily” as separate canonical labels because cadence changes the product semantics.
7. Alias rule: aliases are alternate human-readable names that may appear in review or source data, but should not become separate records. For Birth Control, all brand-equivalent names belong in `brand_equivalents` and may also be copied into `aliases`. For Sexual Health, generic-and-brand pairs like sildenafil and Viagra should remain one canonical option with brand alias support unless the implementation deliberately wants separate marketed names for output variation.
8. Tagging rule: tags should be machine-friendly and composable. Minimum recommended tag families are domain tags, category tags, formulation tags, cadence tags, route tags, ingredient tags, and clinical-use tags. Example tags include `combined-ocp`, `progestin-only`, `male-pattern`, `female-pattern`, `topical`, `oral`, `chewable`, `gummy`, `spray`, `serum`, `pill`, `daily`, `prn`, `ssri`, `pde5i`, `pe`, `ed`, `compounded`, `generic`, `combo-product`, `contains-finasteride`, `contains-minoxidil`, `contains-fluoxetine`, `contains-atorvastatin`.
9. Ingredient extraction rule: split combination products into structured `active_ingredients` records whenever ingredients are explicitly named. Each ingredient entry should support `name`, `strength`, and optional `unit`. If exact strengths are unavailable in the source string, keep the ingredient name and leave structured strength null while preserving the original text in `strength_text`.
10. Strength parsing rule: preserve the raw strength string exactly in `strength_text`, and populate `strength_values` only when values can be parsed confidently. For single products, store one parsed strength entry. For combinations, store one parsed entry per ingredient when the mapping is explicit. For birth control lines that contain multiple estrogen/progestin stages or iron components, preserve the whole display label and parse into a list rather than forcing a lossy simplification.
11. Cadence normalization rule: infer cadence only when clearly encoded. Normalize to a small enum such as `daily`, `prn`, `monthly-count`, or `unknown`. Do not guess cadence from drug class alone. For propranolol with “4, 6, 8, 10, or 12 pills per month”, store cadence as `monthly-count` and keep the numbers in `pill_count_options`.
12. Form and route rule: split dosage form from route whenever possible. Recommended `form` values include `tablet`, `chewable-tablet`, `pill`, `gummy`, `spray`, `serum`, `solution`. Recommended `route` values include `oral` and `topical`. If the source only implies one of these, fill the confident field and leave the other null.
13. Birth-control specific rule: each EMR display line should become the canonical record, and the following brand-equivalent line should attach to that record, not produce new records. Store the hormone pattern in tags such as `monophasic`, `biphasic`, `triphasic`, `extended-cycle`, and `with-iron` when present. Preserve estrogen and progestin components as active ingredients.
14. Hair-loss specific rule: male-pattern and female-pattern sections should be retained as `subdomain` because they are clinically meaningful generation filters. Products that differ only by supplemental blend wording but represent distinct marketed options should remain separate records if the phrasing is expected to appear in synthetic output. Keep topical spray, topical serum, chewable, gummy, pill, and generic oral minoxidil options distinct.
15. Sexual-health specific rule: separate `pde5i`, `combo-pde5i`, and `ssri-pe` categories. Treat daily and PRN variants as separate canonical records. Combination products that include non-sexual-health ingredients, such as atorvastatin, minoxidil, finasteride, multivitamin blend, or testosterone support blend, should keep those ingredients/tags because they affect scenario selection and wording.
16. Performance-anxiety specific rule: normalize propranolol as one canonical medication family with either multiple child variants or one record with `pill_count_options`, depending on implementation convenience. The safer default is one canonical record with `pill_count_options: [4,6,8,10,12]` so scenario templates can inject quantity without duplicating medication rows.
17. Output-variation rule: generation should use `canonical_label` by default. Alias or brand-name substitution should be optional and controlled by an explicit variation setting so the default dataset remains consistent and deduplication stays tractable.
18. Preservation rule: every normalized record must keep the original unmodified source line in `source_text` and any lossy parsing notes in `notes`. If parsing confidence is low, prefer preserving raw text plus tags over inventing structured values.
19. Validation rule: reject or flag normalized records that lack a domain, have duplicate IDs, collapse two distinct products into one canonical label, or produce empty canonical labels after cleanup. Also flag any record where a cadence or ingredient was inferred without direct textual support.
20. Review-app rule: normalized medication records should be reviewable independently before synthetic row generation. The review UI should be able to filter by domain, subdomain, tag, ingredient, and cadence, because medication normalization errors will otherwise contaminate all generated rows downstream.

**Further Considerations**
1. Medication ingest format should be standardized early. Recommendation: accept one file per domain with canonical medication label, optional aliases, and optional tags such as `daily`, `as_needed`, `combo`, `topical`, or `chewable`.
2. The final output-only training file can stay minimal, but keeping a second audit file is important for regeneration and QA; otherwise once rows are flattened there is no clean way to trace why a line was produced.
3. Once the deterministic pipeline is stable, LLM paraphrasing can be added as an optional post-processing stage for selected scenarios instead of the default generator path.
